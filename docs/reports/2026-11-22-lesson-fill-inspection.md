В архивном HTML практического журнала присутствуют штатные кнопки **«Привязать КТП»**, **«Сброс привязки к КТП»**, **«Закрыть занятие»**, **«Открыть занятие»**, а также два набора ячеек сетки (\`.x-grid3-locked\` и \`.x-grid3-unlocked\`). Заголовок каждого занятия имеет отдельный ключ столбца \`x-grid3-td-...\`; скрытая ячейка первой строки содержит числовой ID занятия. Наблюдается повторение календарной даты в разных занятиях, поэтому привязываться к дате без ID нельзя.

## Что не подтверждено и почему нельзя отправлять прямые запросы

1. В JSON нет HTTP-методов, тел запросов, параметров формы и ответов; списки \`parameters\` пусты. Статус HTTP 200 не равнозначен подтверждению изменения записи.
2. Не установлены ID выбранной строки КТП, передаваемый тип оценки, идентификатор студента в \`save_lesson_score\` и параметры закрытия.
3. Не зафиксирована итоговая проверка закрытого состояния на сервере; открытие дополнительного окна не доказывает завершение закрытия.
4. Возможно наличие уже внесённых оценок, пропусков и особенностей разных типов журналов. Массовая операция без read-back может перезаписать значимые данные.

## Реализация в дашборде (1.6.0)

Добавлен локальный план \`workflow:plan:<journal-key>\` с номерами тем КТП для отдельных ID занятий, отметками подготовки троек и ручным подтверждением трёх этапов. Кнопки перехода находят нужное занятие **по ID**, проверяя группу, дисциплину и тип журнала, и подсвечивают столбец в БАРС. Это гарантированно **не является отправкой оценок, привязкой КТП или закрытием занятия**.

Для следующего этапа необходима отдельная инспекция, которая регистрирует **названия полей запроса, тип HTTP-операции и проверяемый результат после обновления** (без токенов, cookie, ФИО и других персональных данных). Затем можно реализовать штатные UI-действия с проверкой результата после каждой записи, паузами и возможностью остановки.
